# 결제 API k6 테스트

## 공통 실행 조건

- k6 설치 및 환경변수 설정은 상위 `k6/README.md` 참고
- 모든 명령어는 `k6` 디렉토리에서 실행
- 테스트 회원은 `setup/create-users.js`를 통해 사전 생성
- 결제 가능한 PENDING 상태의 주문 데이터 사전 준비
- Toss Payments 실제 API 호출을 방지하기 위해 WireMock 사용
- Spring Boot는 `k6` 프로필로 실행
- 실제 운영 환경이 아닌 테스트 전용 환경에서 실행
- 배포 환경에서는 `BASE_URL` 및 Mock 서버 연결 설정을 테스트 환경에 맞게 변경

## 1. 결제 승인 테스트

### 테스트 목적

- 결제 승인 API가 정상적으로 동작하는지 검증
- 결제 승인 후 주문 및 결제 상태 변경 확인
- DB 데이터 정합성 및 응답 시간 측정

### 대상 API

`POST /api/payments/confirm`

### 테스트 데이터 준비

- 테스트 회원 1번 계정 사용
- 해당 회원의 PENDING 상태 주문 1건 생성
- 주문 만료 시간(10분) 이내에 테스트 실행
- 주문의 Toss 주문 ID와 결제 금액 확인
- WireMock 결제 승인 응답 설정

### 환경변수

```dotenv
TOSS_ORDER_ID=8e371b32fe6544519caf2f15f41177b8
PAYMENT_AMOUNT=18000
PAYMENT_KEY=mock-payment-002
```

※ 위 값은 로컬 테스트에서 사용한 데이터이며, 재실행 시 새로운 PENDING 주문과 결제 키를 사용해야 한다.

### 실행 방법

```bash
k6 run payment/payment-confirm-test.js
```

| p95 응답 시간 | 267.83ms |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---|---|
| 주문 상태 | PAID | PAID |

모든 k6 Threshold를 통과하였으며 DB 데이터 정합성 검증을 완료하였다.

## 2. 동일 주문 중복 결제 승인 방지 테스트

### 테스트 목적

동일 회원이 동일 주문에 대해 여러 결제 승인 요청을 동시에 전송했을 때 중복 결제가 발생하지 않는지 검증한다.

결제 승인 API의 멱등성 및 외부 결제 API 중복 호출 방지 여부를 확인한다.

### 대상 API

`POST /api/payments/confirm`

### 테스트 데이터 준비

- 테스트 회원 1번 계정 사용
- PENDING 상태의 주문 1건 생성
- 주문 만료 시간(10분) 이내에 테스트 실행
- 동일 주문 ID, 결제 키, 결제 금액 사용
- WireMock 결제 승인 API 정상 응답 설정
- 테스트 환경의 HikariCP 최대 커넥션 수 20으로 설정

### 환경변수

```dotenv
VUS=10
TOSS_ORDER_ID=실제_주문의_TOSS_ORDER_ID
PAYMENT_AMOUNT=119000
PAYMENT_KEY=mock-duplicate-002
```

※ 주문 ID 및 결제 키는 테스트 환경에 맞게 변경한다. 결제 금액은 실제 주문 금액과 일치해야 한다.

### 실행 방법

```bash
k6 run payment/payment-duplicate-test.js
```

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 가상 사용자 | 10명 |
| 결제 승인 요청 | 10건 |
| HTTP 200 응답 | 10건 |
| 중복 처리 거절 | 0건 |
| 예상하지 못한 오류 | 0건 |
| 평균 응답 시간 | 96.48ms |
| p95 응답 시간 | 107.84ms |
| HTTP 실패율 | 0% |
| 응답 검증 성공률 | 100% |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---|---|
| 주문 상태 | PAID | PAID |
| 생성된 결제 데이터 | 1건 | 1건 |
| 중복 결제 데이터 | 0건 | 0건 |
| 동일 결제 키의 WireMock 승인 요청 | 1건 | 1건 |
| 예상하지 못한 오류 | 0건 | 0건 |

동일 주문에 결제 승인 요청 10건을 동시에 전송한 결과, 모든 요청이 HTTP 200으로 정상 처리되었다.

DB에서는 주문이 PAID 상태로 변경되고 결제 데이터가 1건만 저장된 것을 확인하였다.

WireMock 요청 기록에서도 해당 결제 키에 대한 외부 결제 승인 API 호출이 1건만 발생한 것을 확인하였다.

이는 이미 승인된 결제에 대한 재요청이 기존 결제 정보를 반환하는 멱등 처리 방식으로 동작한 결과로 판단된다.

### 테스트 중 발생한 문제 및 해결

최초 동시성 테스트에서는 10건의 요청이 모두 타임아웃되었다.

서버 로그 분석 결과, 결제 처리 과정에서 사용하는 `REQUIRES_NEW` 트랜잭션이 별도의 DB 커넥션을 요청하면서 HikariCP 커넥션 풀이 부족해지는 문제가 발생하였다.

이에 k6 테스트 환경에서 HikariCP 최대 커넥션 수를 20으로 조정하고 테스트를 재실행하였다.

재실행 결과 동시 요청 10건 모두 정상 처리되었으며, 결제 데이터 중복 생성 없이 테스트를 통과하였다.

### 배포 환경 테스트 계획

| 단계 | VU | 결제 승인 요청 | 예상 정상 처리 | 중복 결제 |
|---|---:|---:|---:|---:|
| 1차 | 10 | 10건 | 10건 | 0건 |
| 2차 | 30 | 30건 | 30건 | 0건 |
| 3차 | 50 | 50건 | 50건 | 0건 |
| 4차 | 100 | 100건 | 100건 | 0건 |

### 배포 환경 실행 예시

```bash
k6 run -e VUS=10 payment/payment-duplicate-test.js

k6 run -e VUS=30 payment/payment-duplicate-test.js

k6 run -e VUS=50 payment/payment-duplicate-test.js

k6 run -e VUS=100 payment/payment-duplicate-test.js
```

각 단계는 독립적으로 실행하며 새로운 PENDING 주문과 결제 키를 사용한다.

테스트 종료 후 결제 데이터가 1건만 생성되었는지, 외부 결제 승인 API가 중복 호출되지 않았는지 검증한다.

동시성 테스트에서는 HTTP 200 또는 예상된 HTTP 409(PAYMENT_PROCESSING)를 정상 처리로 인정한다.

배포 환경에서는 HikariCP 커넥션 풀 사용량, 트랜잭션 대기 시간 및 DB 락 경합을 추가로 확인한다.

※ 30~100 VU 테스트는 아직 실행하지 않았으며, 실제 서버의 커넥션 풀과 동시 처리 용량을 확인한 후 단계적으로 진행한다.

## 3. 서로 다른 주문 동시 결제 승인 테스트

### 테스트 목적

서로 다른 회원이 각각 생성한 주문에 대해 동시에 결제 승인 요청을 전송했을 때 모든 결제가 정상적으로 처리되는지 검증한다.

동시 결제 처리 과정에서 발생할 수 있는 트랜잭션 충돌, DB 커넥션 풀 부족 및 결제 데이터 정합성 문제를 확인한다.

### 대상 API

`POST /api/orders`

`POST /api/payments/confirm`

### 테스트 데이터 준비

- 서로 다른 테스트 회원 10명
- 판매 가능한 OPEN 상태의 상품 1개
- 상품 ID 26번 사용
- 초기 재고 30개
- 1인 구매 제한 5개
- 각 회원이 상품 1개씩 주문
- `setup()`에서 회원별 PENDING 주문 10건 자동 생성
- 생성된 주문의 Toss 주문 ID와 결제 금액을 사용
- WireMock을 통한 Toss Payments 결제 승인 API Mock 처리
- HikariCP 최대 커넥션 수 20으로 설정

### 환경변수

```dotenv
VUS=10
PRODUCT_ID=26
```

상품 ID는 테스트 환경의 실제 데이터에 맞게 변경한다.

테스트 상품은 충분한 재고와 구매 가능 수량이 확보되어 있어야 한다.

### 실행 방법

```bash
k6 run payment/payment-concurrency-test.js
```

테스트 실행 시 `setup()`에서 회원 10명이 로그인하고 각각 주문 1건을 자동 생성한다.

이후 10개의 VU가 각자 생성된 주문에 대해 결제 승인 요청을 동시에 전송한다.

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 테스트 회원 | 10명 |
| 가상 사용자 | 10명 |
| 주문 자동 생성 | 10건 |
| 결제 승인 요청 | 10건 |
| 결제 승인 성공 | 10건 |
| 예상하지 못한 오류 | 0건 |
| 평균 HTTP 응답 시간 | 92.85ms |
| p95 HTTP 응답 시간 | 186.65ms |
| HTTP 실패율 | 0% |
| 응답 검증 성공률 | 100% |
| 전체 HTTP 요청 | 30건 |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

※ HTTP 응답 시간은 로그인 10건, 주문 생성 10건, 결제 승인 10건을 포함한 전체 요청 기준이다.

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---:|---:|
| 주문 상태 PAID | 10건 | 10건 |
| 결제 상태 PAID | 10건 | 10건 |
| 결제 승인 성공 | 10건 | 10건 |
| WireMock 결제 승인 API 호출 | 10건 | 10건 |
| 예상하지 못한 오류 | 0건 | 0건 |

서로 다른 회원 10명이 각각 주문을 생성한 후 동시에 결제 승인 요청을 전송한 결과, 모든 요청이 정상적으로 처리되었다.

DB 조회 결과 주문 상태와 결제 상태가 모두 PAID인 데이터 10건을 확인하였다.

WireMock 요청 기록에서도 테스트 결제 키(`mock-concurrent-`)에 해당하는 외부 결제 승인 API 호출이 10건 발생한 것을 확인하였다.

모든 k6 Threshold를 통과하였으며 동시 결제 승인 상황에서도 정상적인 결제 처리와 데이터 정합성이 유지되는 것을 확인하였다.

### 배포 환경 테스트 계획

| 단계 | VU | 테스트 회원 | 주문 생성 | 예상 결제 성공 |
|---|---:|---:|---:|---:|
| 1차 | 10 | 10명 | 10건 | 10건 |
| 2차 | 30 | 30명 | 30건 | 30건 |
| 3차 | 50 | 50명 | 50건 | 50건 |
| 4차 | 100 | 100명 | 100건 | 100건 |

### 배포 환경 실행 예시

```bash
# 10명
k6 run -e VUS=10 payment/payment-concurrency-test.js

# 30명
k6 run -e VUS=30 payment/payment-concurrency-test.js

# 50명
k6 run -e VUS=50 payment/payment-concurrency-test.js

# 100명
k6 run -e VUS=100 payment/payment-concurrency-test.js
```

각 단계는 독립적으로 실행하며 테스트 전에 충분한 재고와 테스트 회원을 준비한다.

주문 생성 후 10분 이내에 결제 승인이 완료되어야 하므로, 테스트 데이터 생성 시간과 주문 만료 시간을 확인한다.

각 단계 종료 후 주문 상태, 결제 상태, 결제 데이터 건수 및 WireMock 승인 요청 횟수를 검증한다.

배포 환경에서는 응답 시간, DB 커넥션 풀 사용량, 트랜잭션 처리 시간 및 서버 자원 사용량을 추가로 확인한다.

※ 30~100 VU 테스트는 아직 실행하지 않았으며, 테스트 환경의 DB 커넥션 풀 크기와 상품 재고 및 구매 제한을 고려하여 단계적으로 진행한다.

## 4. 동일 주문 중복 결제 취소 테스트

### 테스트 목적

결제가 완료된 동일 주문에 여러 취소 요청을 동시에 전송했을 때 중복 결제 취소가 발생하지 않는지 검증한다.

결제 취소 과정에서 주문 및 결제 상태의 정합성이 유지되고, 외부 결제 취소 API가 중복 호출되지 않는지 확인한다.

### 대상 API

`POST /api/orders`

`POST /api/payments/confirm`

`PATCH /api/orders/{orderId}/cancel`

### 테스트 데이터 준비

- 테스트 회원 1번 계정 사용
- 판매 가능한 OPEN 상태의 상품 1개
- 상품 ID 26번 사용
- `setup()`에서 PENDING 상태의 주문 1건 자동 생성
- WireMock을 통해 결제 승인 후 PAID 상태로 변경
- 동일 주문에 취소 요청 10건 동시 전송
- WireMock 결제 취소 API Mock 응답 설정
- HikariCP 최대 커넥션 수 20으로 설정

### 환경변수

```dotenv
VUS=10
PRODUCT_ID=26
```

상품 ID는 테스트 환경의 실제 데이터에 맞게 변경한다.

테스트 회원에게 해당 상품의 구매 가능 수량이 남아 있어야 하며, 상품 재고도 충분해야 한다.

### 실행 방법

WireMock 요청 기록 초기화:

```bash
curl -X POST http://localhost:8089/__admin/requests/reset
```

로컬 테스트 실행:

```bash
k6 run payment/payment-cancel-test.js
```

테스트 실행 시 `setup()`에서 주문 생성 및 결제 승인을 완료한 후, 10개의 VU가 동일 주문에 취소 요청을 동시에 전송한다.

| 주문 자동 생성 | 1건 |
| 결제 승인 | 1건 |
| 동시 취소 요청 | 10건 |
| 결제 취소 성공 | 1건 |
| 중복 취소 거절 | 9건 |
| 예상하지 못한 오류 | 0건 |
| 평균 HTTP 응답 시간 | 79.06ms |
| p95 HTTP 응답 시간 | 102.92ms |
| 응답 검증 성공률 | 100% |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

HTTP 409(`ORDER_ALREADY_CANCELLED`)는 예상된 비즈니스 예외이므로 정상적인 중복 취소 거절로 처리한다.

따라서 k6의 `http_req_failed`가 69.23%로 표시되었지만, 이는 예상된 HTTP 409 응답 9건으로 인한 것이며 테스트 실패를 의미하지 않는다.

※ HTTP 응답 시간은 로그인, 주문 생성, 결제 승인 및 취소 요청을 포함한 전체 HTTP 요청 기준이다.

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---|---|
| 주문 상태 | CANCELLED | CANCELLED |
| 결제 상태 | CANCELLED | CANCELLED |
| 결제 취소 시각 | 저장 | 저장 확인 |
| 취소 성공 | 1건 | 1건 |
| 중복 취소 거절 | 9건 | 9건 |
| WireMock 결제 취소 API 호출 | 1건 | 1건 |
| 상품 26번 현재 재고 | 확인 | 20개 |

주문 133번에 취소 요청 10건을 동시에 전송한 결과, 1건만 정상적으로 취소되고 나머지 9건은 `ORDER_ALREADY_CANCELLED`로 거절되었다.

DB 조회 결과 주문과 결제 상태가 모두 CANCELLED로 변경되었으며, 결제 취소 시각이 정상적으로 저장된 것을 확인하였다.

WireMock 요청 기록에서도 해당 결제에 대한 외부 결제 취소 API 호출이 1건만 발생한 것을 확인하였다.

상품 26번의 테스트 후 재고는 20개로 확인하였다. 단, 정확히 1개의 재고가 복구되었는지는 취소 직전 재고와 비교하는 추가 검증이 필요하다.

모든 k6 Threshold를 통과하였으며, 동일 주문에 대한 중복 취소 요청이 정상적으로 제어되는 것을 확인하였다.

### 배포 환경 실행 예시

```bash
# 10명
k6 run -e VUS=10 payment/payment-cancel-test.js

# 30명
k6 run -e VUS=30 payment/payment-cancel-test.js

# 50명
k6 run -e VUS=50 payment/payment-cancel-test.js

# 100명
k6 run -e VUS=100 payment/payment-cancel-test.js
```

각 단계는 독립적으로 실행하며, `setup()`에서 새로운 주문을 생성하고 결제를 승인한 후 테스트를 진행한다.

테스트 종료 후 주문 및 결제 상태가 CANCELLED인지 확인하고, 외부 결제 취소 API가 정확히 1번 호출되었는지 검증한다.

또한 테스트 전후 상품 재고를 비교하여 재고 복구가 정확히 한 번 수행되었는지 확인한다.

배포 환경에서는 응답 시간, DB 커넥션 풀 사용량, 트랜잭션 처리 시간 및 락 경합 등을 추가로 확인한다.

※ 30~100 VU 테스트는 아직 실행하지 않았으며, 테스트 서버의 처리 용량을 확인한 후 단계적으로 진행한다.
