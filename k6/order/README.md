# 주문 API k6 테스트

## 공통 실행 조건

- k6 설치 및 환경변수 설정은 상위 k6/README.md 참고
- 모든 명령어는 k6 디렉토리에서 실행
- 배포 환경에서는 BASE_URL을 테스트 서버 주소로 변경
- 테스트 회원 및 상품 데이터 사전 준비
- Redis 만료 이벤트 알림 설정 확인
- 실제 운영 환경이 아닌 테스트 전용 환경에서 실행

## 1. 주문 목록 조회 테스트

### 테스트 목적

- 주문 목록 조회 API의 응답 시간 및 처리량 측정
- JWT 인증 및 주문 목록 응답 데이터 검증

### 대상 API

`GET /api/orders`

### 테스트 데이터 준비

- 공통 테스트 회원 1번 계정 사용
- 해당 회원의 주문 데이터 1건 이상 생성
- 별도의 주문 ID 환경변수는 필요하지 않음

### 실행 방법

로컬 Smoke Test:

```bash
k6 run -e SMOKE=true order/order-read-test.js
```

배포 환경 부하 테스트:

```bash
k6 run -e SMOKE=false order/order-read-test.js
```

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 가상 사용자 | 1명 |
| 테스트 시간 | 20초 |
| 주문 조회 요청 | 20건 |
| 평균 응답 시간 | 14.67ms |
| p95 응답 시간 | 22.78ms |
| HTTP 실패율 | 0% |
| 응답 검증 성공률 | 100% (80/80) |
| Threshold | PASS |

### 배포 환경 테스트 계획

| 항목 | 설정 |
|---|---|
| 테스트 회원 | 1명 |
| 주문 데이터 | 10건 이상 권장 |
| 가상 사용자 | 10 → 30 → 50 → 100명 |
| 테스트 시간 | 6분 30초 |
| 요청 간 대기 시간 | 1초 |
| p95 목표 | 1,000ms 미만 |
| HTTP 실패율 | 1% 미만 |
| 응답 검증 성공률 | 99% 초과 |

현재 스크립트는 동일 회원의 주문 목록을 반복 조회하는 방식이다.

실제 다중 회원 조회 부하 테스트가 필요한 경우 회원별 주문 데이터와 JWT를 별도로 준비해야 한다.

배포 환경 테스트 결과는 실행 후 추가 기록한다.

## 2. 동시 주문 재고 초과 판매 방지 테스트

### 테스트 목적

다수의 회원이 동일 상품에 동시에 주문을 요청할 때 재고를 초과하여 판매되는 것을 방지하고, 상품 재고의 정합성을 검증한다.

### 대상 API

`POST /api/orders`

### 테스트 데이터 준비

- 서로 다른 테스트 회원 10명
- 판매 가능한 상품 1개
- 초기 상품 재고 7개
- 요청당 구매 수량 1개
- 테스트 회원의 기존 구매 내역이 구매 제한에 영향을 주지 않아야 함
- 기존 미결제 주문의 만료 처리가 테스트에 영향을 주지 않아야 함

### 환경변수

```dotenv
PRODUCT_ID=28
INITIAL_STOCK=7
VUS=10
```

상품 ID 및 초기 재고는 테스트 환경의 실제 데이터에 맞게 변경한다.

INITIAL_STOCK은 실제 상품 재고를 변경하는 값이 아니라 예상 주문 성공 건수를 계산하기 위한 값이다.

### 실행 방법

```bash
k6 run order/order-stock-test.js
```

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 가상 사용자 | 10명 |
| 초기 재고 | 7개 |
| 주문 요청 | 10건 |
| 주문 성공 | 7건 |
| 재고 부족 거절 | 3건 |
| 예상하지 못한 오류 | 0건 |
| 응답 검증 성공률 | 100% |
| 전체 실행 시간 | 약 1.4초 |
| Threshold | PASS |
| DB 데이터 정합성 | 재실행 결과 확인 예정 |

서로 다른 회원 10명이 동일 상품에 동시 주문 요청을 전송했을 때 초기 재고에 해당하는 7건만 성공하고, 나머지 3건은 INSUFFICIENT_STOCK으로 정상 거절되었다.

모든 k6 Threshold를 통과하였으며 예상하지 못한 오류는 발생하지 않았다.

HTTP 409(INSUFFICIENT_STOCK)는 예상된 비즈니스 예외이므로 정상 거절로 처리한다.

기존 실행에서 재고가 모두 차감된 상태로 테스트를 재실행하여 성공 및 거절 건수 Threshold가 실패하였다.

기존 주문의 만료 및 재고 복구를 확인한 후 동일한 초기 조건에서 재검증한다.

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---:|---:|
| 신규 PENDING 주문 | 7건 | 7건 |
| 주문 상품 수량 합계 | 7개 | 7개 |
| 초기 재고 | 7개 | 7개 |
| 최종 재고 | 0개 | 0개 |
| 재고 초과 판매 | 0건 | 0건 |
| 주문 만료 후 재고 | 7개 | 0개 |

DB에서 신규 주문 7건이 생성되었으며 상품 재고가 0개로 차감된 것을 확인하였다.

HTTP 409(INSUFFICIENT_STOCK)는 예상된 비즈니스 예외이므로 정상 거절로 처리한다.

### 배포 환경 테스트 계획

| 단계 | VU | 초기 재고 | 예상 성공 | 예상 거절 |
|---|---:|---:|---:|---:|
| 1차 | 10 | 5 | 5 | 5 |
| 2차 | 30 | 15 | 15 | 15 |
| 3차 | 50 | 25 | 25 | 25 |
| 4차 | 100 | 50 | 50 | 50 |

최대 100명의 서로 다른 테스트 회원을 준비한다.

### 배포 환경 실행 예시

```bash
k6 run -e VUS=10 -e INITIAL_STOCK=5 order/order-stock-test.js

k6 run -e VUS=30 -e INITIAL_STOCK=15 order/order-stock-test.js

k6 run -e VUS=50 -e INITIAL_STOCK=25 order/order-stock-test.js

k6 run -e VUS=100 -e INITIAL_STOCK=50 order/order-stock-test.js
```

각 단계는 독립적으로 실행하며 실제 DB의 상품 재고를 INITIAL_STOCK과 동일하게 준비한다.

테스트 종료 직후 신규 주문 건수, 주문 상품 수량 합계 및 최종 상품 재고를 검증한다.

PENDING 주문은 10분 후 만료되므로 만료 처리 전에 DB 상태를 확인한다.

반복 실행 전 기존 주문의 만료 처리 및 상품 재고 복구 여부를 반드시 확인한다.

배포 환경에서는 응답 시간, 서버 자원 사용량, DB 커넥션 풀 사용량 및 상품 재고 락 경합 등을 추가로 확인한다.

## 3. 1인 구매 수량 제한 테스트

### 테스트 목적

동일 회원이 동일 상품에 여러 주문 요청을 동시에 전송했을 때 1인 최대 구매 수량을 초과하지 않는지 검증한다.

### 대상 API

`POST /api/orders`

### 테스트 데이터 준비

- 공통 테스트 회원 1번 계정 사용
- 판매 가능한 상품 1개
- 초기 재고 80개
- 1인 최대 구매 수량 2개
- 해당 회원의 기존 PENDING 및 PAID 구매 내역이 없어야 함

### 환경변수

```dotenv
LIMIT_PRODUCT_ID=27
MAX_QTY=2
VUS=10
```

상품 ID 및 구매 제한 수량은 테스트 환경의 실제 데이터에 맞게 변경한다.

### 실행 방법

```bash
k6 run order/order-limit-test.js
```

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 테스트 회원 | 1명 |
| 가상 사용자 | 10명 |
| 초기 재고 | 80개 |
| 1인 구매 제한 | 2개 |
| 주문 요청 | 10건 |
| 주문 성공 | 2건 |
| 구매 제한 초과 거절 | 8건 |
| 예상하지 못한 오류 | 0건 |
| 응답 검증 성공률 | 100% |
| 전체 실행 시간 | 약 0.7초 |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

### DB 데이터 정합성 검증

| 검증 항목 | 예상 결과 | 실제 결과 |
|---|---:|---:|
| 신규 PENDING 주문 | 2건 | 2건 |
| 주문 상품 수량 합계 | 2개 | 2개 |
| 초기 재고 | 80개 | 80개 |
| 최종 재고 | 78개 | 78개 |
| 구매 제한 위반 | 0건 | 0건 |

동일 회원이 동일 상품에 동시 주문 요청 10건을 전송했을 때 최대 구매 수량에 해당하는 2건만 성공하고, 나머지 8건은 PURCHASE_LIMIT_EXCEEDED로 정상 거절되었다.

모든 k6 Threshold를 통과했으며 DB에서도 주문 2건이 생성되고 상품 재고가 정확하게 차감된 것을 확인하였다.

HTTP 409(PURCHASE_LIMIT_EXCEEDED)는 예상된 비즈니스 예외이므로 정상 거절로 처리한다.

### 배포 환경 테스트 계획

| 단계 | VU | 구매 제한 | 예상 성공 | 예상 거절 |
|---|---:|---:|---:|---:|
| 1차 | 10 | 2 | 2 | 8 |
| 2차 | 30 | 2 | 2 | 28 |
| 3차 | 50 | 2 | 2 | 48 |
| 4차 | 100 | 2 | 2 | 98 |

### 배포 환경 실행 예시

```bash
k6 run -e VUS=10 order/order-limit-test.js

k6 run -e VUS=30 order/order-limit-test.js

k6 run -e VUS=50 order/order-limit-test.js

k6 run -e VUS=100 order/order-limit-test.js
```

각 단계는 독립적으로 실행하며 상품 재고는 충분하게 유지한다.

테스트 전 해당 회원의 기존 활성 구매 내역을 확인하고, 테스트 종료 직후 신규 주문 건수 및 구매 수량, 상품 재고를 검증한다.

배포 환경에서는 사용자 락 경합 및 DB 커넥션 풀 사용량도 추가로 확인한다.

## 4. 중복 주문 취소 및 재고 중복 복구 방지 테스트

### 테스트 목적

동일한 PENDING 주문에 대해 여러 취소 요청이 동시에 발생했을 때 주문 취소는 한 번만 성공하고, 상품 재고가 중복 복구되지 않는지 검증한다.

### 대상 API

`PATCH /api/orders/{orderId}/cancel`

### 테스트 데이터 준비

- 공통 테스트 회원 1번 계정 사용
- 상품 ID: 26
- 주문 전 상품 재고: 30개
- 주문 수량: 1개
- 주문 생성 후 상품 재고: 29개
- 테스트 대상: 결제되지 않은 PENDING 주문
- 취소 요청 전 주문 만료 여부 확인

### 환경변수

```dotenv
CANCEL_ORDER_ID=109
VUS=10
```

주문 ID는 매번 새로 생성한 PENDING 주문의 ID로 변경한다.

### 실행 방법

```bash
k6 run order/order-cancel-test.js
```

### 로컬 테스트 결과

| 항목 | 결과 |
|---|---:|
| 가상 사용자 | 10명 |
| 취소 요청 | 10건 |
| 취소 성공 | 1건 |
| 중복 취소 거절 | 9건 |
| 예상하지 못한 오류 | 0건 |
| 응답 검증 성공률 | 100% |
| 평균 HTTP 응답 시간 | 120.1ms |
| p95 HTTP 응답 시간 | 141.81ms |
| 전체 실행 시간 | 약 0.3초 |
| Threshold | PASS |
| DB 데이터 정합성 | PASS |

HTTP 409(ORDER_ALREADY_CANCELLED)는 예상된 비즈니스 예외이므로 정상 거절로 처리한다.

### DB 데이터 정합성 검증

| 검증 항목 | 실제 결과 |
|---|---|
| 주문 ID | 109 |
| 최종 주문 상태 | CANCELLED |
| 상품 ID | 26 |
| 주문 전 재고 | 30개 |
| 취소 후 재고 | 30개 |
| 중복 재고 복구 | 발생하지 않음 |

동일 주문에 대해 취소 요청 10건을 전송한 결과, 1건만 정상 취소되고 나머지 9건은 ORDER_ALREADY_CANCELLED로 거절되었다.

모든 k6 Threshold를 통과하였으며 DB에서 주문 상태가 CANCELLED이고 상품 재고가 정상 복구된 것을 확인하였다.

### 배포 환경 테스트 계획

| 단계 | VU | 예상 성공 | 예상 중복 취소 거절 |
|---|---:|---:|---:|
| 1차 | 10 | 1 | 9 |
| 2차 | 30 | 1 | 29 |
| 3차 | 50 | 1 | 49 |
| 4차 | 100 | 1 | 99 |

각 단계는 서로 다른 신규 PENDING 주문으로 독립적으로 실행한다.

### 배포 환경 실행 예시

```bash
k6 run -e VUS=10 order/order-cancel-test.js

k6 run -e VUS=30 order/order-cancel-test.js

k6 run -e VUS=50 order/order-cancel-test.js

k6 run -e VUS=100 order/order-cancel-test.js
```

각 테스트 전에 `CANCEL_ORDER_ID`를 새 주문 ID로 변경한다.

테스트 후 주문 상태와 상품 재고가 정확히 한 번만 복구되었는지 확인한다.

배포 환경에서는 동시 취소 처리 시 주문 잠금 경합, DB 커넥션 풀 사용량 및 응답 시간을 추가로 모니터링한다.
